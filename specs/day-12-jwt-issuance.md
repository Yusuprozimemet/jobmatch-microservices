# Day 12 — JWT issuance and JWKS

**Phase:** 2 · **Depends on:** Day 11 · **Expected PRs:** 4

## Goal
`identity` can mint and publish verifiable tokens. Nothing consumes them yet — sessions
still work exactly as before.

## In scope
- **One RSA signing key, from a file.** `JWT_PRIVATE_KEY_FILE` (property
  `app.jwt.private-key-file`) names a PEM, PKCS#8, RSA private key of at least 2048 bits. The
  public key is derived from it, and the key id is its RFC 7638 thumbprint, so there is no
  second setting to keep in step. It is never generated by the application, in any profile: a
  restart would invalidate every token.
- **No key, no start.** With the variable unset, the file missing, or a file that is not an RSA
  private key, the application fails to start with a message naming `JWT_PRIVATE_KEY_FILE`.
  That applies to compose and to the test suite too, so both get a key without one in git:
  - **Compose** gets a one-shot service that writes a key into a named volume when the volume
    has none, and exits. The backend depends on it (`service_completed_successfully`), mounts the
    volume read-only, and runs as UID 1000 (`backend/Dockerfile`), so the file must be readable
    by that user. A restart keeps the key; `docker compose down -v` replaces it. The script it
    runs lives in `scripts/`, is pinned to LF by `.gitattributes`, and is the one a developer
    runs by hand to start the backend outside compose.
  - **The test harness** generates a key once per run in `support/` and passes its path with a
    `DynamicPropertySource`, as it already does for the database.
- **Access token**, RS256, 15 minutes: `sub` = the user's UUID, plus `email`,
  `iss` = `jobmatch-identity`, `aud` = `jobmatch-api`, `iat`, `exp`, and a random `jti`. The
  `jti` is not decoration: RS256 signatures are deterministic and `iat` is in whole seconds, so
  without it two tokens for the same user in the same second are identical, and from Day 13
  `AuthPasswordUpdateIT.leavesTheCallerSignedIn` (which asserts the cookie changes) would fail
  whenever login and the password change land in one second.
- **Refresh token:** 32 random bytes, base64url, opaque; 30 days; revocable. Only its SHA-256
  is stored. A slow hash like bcrypt buys nothing for 256 random bits and would prevent looking
  the token up by its hash.
- **`identity.refresh_tokens`**: `id`, `user_id` → `users(id)` **`ON DELETE CASCADE`**,
  `token_hash` (unique), `created_at`, `expires_at`, `revoked_at`. It is
  `identity/src/main/resources/db/identity/V1__refresh_tokens.sql`: identity's first migration,
  applied by identity's own Flyway as `identity_user`, with unqualified names
  (`db/identity/README.md`). The cascade is what keeps `SessionWithoutAUserIT` and
  `AccountDeletionIT` green once Day 13 writes rows at login. Add it to `backend/docs/auth.md`
  §8, which lists what deleting an account removes.
- **Only `identity` can read it, in every environment.** In production `scripts/db-setup.py`
  registers default privileges for every role that creates tables, `identity_user` included,
  so every other role could read the hashes of a table `identity_user` creates. The compose
  init script and the test harness register none, so a test there could never see it. So: the
  migration revokes every privilege on `refresh_tokens` held by any role other than its owner,
  found in the catalogue rather than named; and `scripts/db-init/module-roles.sh` and
  `support/PostgresContainer` register the same default privileges `db-setup.py` does, so all
  three environments agree and the check below can fail.
- `GET /.well-known/jwks.json` — public, no auth (a `permitAll` in `SecurityConfig`), serves
  the public key only. It is outside `/api`, so the Next.js proxy does not forward it: it is for
  the gateway (Day 15), not the browser.
- **Issued by a service, not by login.** Minting, `issue`, `redeem` and `revoke` are methods on
  `identity` beans, in a package of their own, not in `auth/`. `redeem` returns the user for a
  live token and nothing for a revoked, expired or unknown one; it does not rotate (Day 13).
  Login, password change and Google sign-in do not call them until Day 13 wires them in, so this
  day changes no behaviour by construction, and no response gains a cookie or a field.
- The tests of those beans live outside `contract/`, in `app/src/test/.../tokens/`. They extend
  `IntegrationTest` for the database and the port and autowire the beans, as
  `database/ModuleConnectionsIT` does; the "never a bean" rule is for `contract/`.
- New `@Transactional` code names `identityTransactionManager`. There are four transaction
  managers since Day 11 and none is primary.
- **Two harness tests change on purpose, in Track B**, because they pin the layout this day
  adds to: `BackendApplicationTests.flywayHasMovedEachModulesTablesIntoItsOwnSchema` lists
  identity's tables exactly and gains `refresh_tokens identity_user`, and
  `ModuleMigrationsIT.andItStartsAtTheBaseline` pins identity's history at `0 BASELINE` and gains
  `1 SQL` for identity. Neither is in `contract/`. The first is a Day 01 harness self-test, so
  the edit was decided before the work (see Notes), as Day 11 decided it for the same test.

## Out of scope
- Using the token to authenticate, cookies, `POST /api/auth/refresh`, rotation, and revoking at
  logout — Day 13.
- Google sign-in — Day 14.
- More than one key in the JWKS, and key rotation — later; the key id is there so a second key
  can be added without breaking verification.
- `user_credentials.refresh_token_hash` (V2) — see Notes.

## Acceptance criteria
- [ ] **new** — `GET /.well-known/jwks.json` with no cookie returns 200 and exactly one key,
      with `kty` `RSA`, `use` `sig`, `alg` `RS256` and a `kid`, and none of the private members
      `d`, `p`, `q`, `dp`, `dq`, `qi` (asserted by name, `tokens/JwksIT`). Red today: 401 with an
      empty body, from `SecurityConfig`'s `anyRequest().authenticated()`.
- [ ] **new** — An access token minted by `identity` verifies with nimbus-jose-jwt against the
      key the JWKS response publishes, chosen by `kid`, and fails to verify once one byte of its
      signature is changed (`tokens/AccessTokenIT`). Red today: nothing mints a token;
      `grep -rilE "jwk|jwt|well-known" --include=*.java */src/main` from `backend/` finds 0 files.
- [ ] **new** — Its claims: `sub` is the user's UUID, not their email; `email`;
      `iss` = `jobmatch-identity`; `aud` = `jobmatch-api`; `exp − iat` = 900; a `jti`; and two
      tokens minted for one user in the same second differ (`tokens/AccessTokenIT`). Red today:
      nothing mints a token.
- [ ] **new** — A refresh token is unreadable in the database: no column of its row contains
      it, `token_hash` is its SHA-256, and `expires_at` is 30 days after `created_at`
      (`tokens/RefreshTokensIT`). Red today: `identity.refresh_tokens` does not exist.
- [ ] **new** — `redeem` returns the user for a live token and nothing for a revoked, an expired
      or an unknown one (`tokens/RefreshTokensIT`). Red today: no redeem or revoke exists.
- [ ] **new** — Deleting a user deletes their refresh tokens (`tokens/RefreshTokensIT`). Red
      today: the table does not exist; red again with the cascade taken off the foreign key.
- [ ] **new** — As `applications_user`, `matching_user` and `jobs_user`, `SELECT` on
      `identity.refresh_tokens` is refused, in a harness that registers `db-setup.py`'s default
      privileges (`tokens/RefreshTokenGrantsIT`). Red today: the table does not exist; red again,
      with the default privileges in place, when the migration's revoke is removed.
- [ ] **new** — With `JWT_PRIVATE_KEY_FILE` unset, pointing at no file, or at a file that is not
      an RSA private key, the application fails to start with a message naming
      `JWT_PRIVATE_KEY_FILE`. The test starts its own context, not `IntegrationTest`'s, which has a
      key (`tokens/SigningKeyStartupTest`). Red today: all 232 tests start with no key configured.
- [ ] **new** — `docker compose restart backend` serves the same `kid` as before it. Red today:
      there is no JWKS.
- [ ] **hold** — A clean `docker compose up`, with `.env` copied from `.env.example`, starts the
      backend with no manual step (Day 11's hold, now with a key to find). Broken on purpose in
      Track A's PR: without the key step, the backend exits naming `JWT_PRIVATE_KEY_FILE`.
- [ ] **hold** — No behaviour changes. The full suite passes; nothing in `contract/` (23 classes)
      changes; and the three callers of `establishSession`, in `identity/.../auth/`, are
      untouched: the last command in **Verify** prints nothing. The two harness tests above are
      the named exception, outside `contract/`. Broken on purpose in the spec-change PR: with

## Notes
- The key lives in a compose volume for local, Key Vault later. Never in git.
- 15 minutes is short on purpose: it caps the damage from a token we cannot revoke.
- **Spec corrected on Day 09, before the work, from a read of every remaining spec.**
  The verify command ran no tests, for the reason Day 08 found: `-Dtest` with no `-pl` fails
  on `shared` before reaching `app`. Check the surefire reports, not only the exit code.
- **Spec corrected on Day 12, before the work.** The plan-auditor on Phases 1 and 2 and the
  spec-auditor on this day, each in a fresh context, found:
  - **Neither check could fail.** The curl printed its expected `0` with no backend running
    (curl exit 7) and again against today's 401, and it looked for `d` alone of six private
    members. `-Dtest='Jwt*,Auth*IT'` selected 0 classes for `Jwt*` and 49 of 232 tests, so the
    "unedited" criterion was never run by Verify.
  - **No criterion was tagged `new` or `hold`,** the rule since #55.
  - **"No keypair, no start" and "never in git" could not both hold** with Day 11's clean
    `docker compose up`: compose's environment comes from `.env.example`, which is in git, and
    compose runs the `prod` profile (`SPRING_PROFILES_DEFAULT=prod` in the Dockerfile), so a
    dev-only fallback would not have reached it. Line 10 ("never generated at startup in prod")
    and the criterion ("fails to start") also disagreed on whether dev may generate one. Decided
    by the maintainer: a compose step writes a key into a volume.
  - **Where tokens were issued was not said,** and nothing can redeem a refresh token before
    Day 13's endpoint. Decided by the maintainer: beans only, login untouched until Day 13.
  - **Identity's first migration breaks two harness tests by construction.** Tried in a scratch
    copy with a probe `V1` in `db/identity`: `Tests run: 233, Failures: 2`,
    `BackendApplicationTests` (identity's table list) and
    `ModuleMigrationsIT.andItStartsAtTheBaseline` (`["0 BASELINE", "1 SQL"]`). Decided by the
    maintainer before the work, as CLAUDE.md requires for a Day 01 test: update both in Track B.
  - **The migration had no location, no delete rule and no grants.** Without the cascade,
    Day 13's login rows would break `SessionWithoutAUserIT` and `AccountDeletionIT`; without the
    revoke, production alone would let three other roles read the hashes.
  - **`jti` was missing,** and its absence would surface on Day 13 as an intermittent
    `AuthPasswordUpdateIT` failure.
  - `iss` and `aud` had no values and no criterion checked the claims, the TTL or JWKS's
    permit. No test noticed a new cookie at login either (the spec-auditor tried
    `Set-Cookie: access_token=scratch`: all green), which is why issuance stays off login.
  - Tracks were described as parallel, but C needs A's key and A must bring the harness's key

    `StubOidcProvider` uses it.
